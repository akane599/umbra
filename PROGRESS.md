# Progress: Umbra 1.2.1 (touch lock + stay awake)
_Updated: 2026-11-07_

## Goal
Umbra (`io.github.akane599.umbra`, https://github.com/akane599/umbra) ships three modes: panel off, touch lock, stay awake. 1.2 is pushed and running on the owner's phone.

## Done
- Touch lock lets injected touches through (branch `feat/touch-passthrough`, uncommitted, 2026-11-07): `adb shell input tap`, scrcpy and other shell/root tools reach the app under the lock; screen touches stay blocked. Injected events reach windows with device id -1 (InputDispatcher), so `LockView` sends them to `TouchRelay.kt`, which records each gesture and, once it ends, opens a 5×5 px hole (`AttachedSurfaceControl.setTouchableRegion`, API 34) and has the helper replay it there (`inject` command, `InputManagerGlobal.injectInputEvent`). With passthrough the window alpha stays at just under `maximumObscuringOpacityForTouch` (0.8) for the whole session, or untrusted-touch occlusion drops the replay; `LockView` draws with gain 1/alpha so it looks the same, and the Dark dim (88%) stops at 78%. (First version dipped the alpha only while a hole was open: the owner saw the dim flicker on every injected touch.) 17 new tests. Tried on the phone 2026-11-07 with the lock visible and touchable (`dumpsys input`: alpha=1, no NOT_VISIBLE): adb taps worked Calculator (9×9=81), an adb swipe scrolled Material Files, an adb long press on the badge didn't unlock, no untrusted-touch drops or injection errors; finger blocking not re-checked (that path is unchanged).
- Same branch: a dimmed touch lock also empties the status bar (owner: the status bar stayed glaringly bright over the dim; it's drawn above any overlay). The helper's `system` command now takes `on`, or `off` and/or `quiet` (`PanelServer.systemFlags`); `quiet` = DISABLE_CLOCK, SYSTEM_INFO, NOTIFICATION_ICONS, ONGOING_CALL_CHIP, DISABLE2_SYSTEM_ICONS. The service sends it when dim > 0 and restores with `system on` (separate `statusQuiet` flag so the "full lock" title and toast still mean full lock only). 5 new tests. Tried on the phone 2026-11-07 with Soft dim and full lock: flags 0x07F70000/0x7, status bar strip max brightness 255 → 52, clock and icons gone; cleared on stop. The 3-button nav bar stays bright when full lock is off (hiding it disables it).
- Screen-on fix for Samsung (merged to main as `d912808`, 2026-11-07): One UI dropped Stay awake's screen wake lock as "abuse wakelock" when the normal timeout ran out (4 min 40 s after the last touch: 5 min timeout minus 20 s dim) and turned the screen off. `ScreenTimeout.kt` now also raises `screen_off_timeout` to `Int.MAX_VALUE` for every screen-on hold (stay awake, touch lock, panel "Keep the phone awake") and restores the user's value; the value is saved first and recovered on service/app start, QS open and boot. Needs WRITE_SETTINGS, granted by the helper (`appops set … WRITE_SETTINGS allow`). 10 new tests; not yet tried on the phone.
- Audit fixes merged to main (`3341bf9..34687ac`, 10 findings; see `.audit/FIX_REPORT.md`). Installed on the phone 2026-11-07. Behavior changes: "Commands from other apps" off by default; restore exits on a secure phone go to the lock screen ("Lock when the screen comes back"); the newest start request wins during transitions.
- 1.2.1: touch lock closes an open keyboard (the only way Samsung's bar leaked under full lock: with a keyboard up it re-enables "hide keyboard" and the keyboard switcher). Verified on the phone with Termux.
- 1.2 pushed (`b43e265`) and installed on the owner's Samsung (Android 17). Touch lock confirmed working by the owner; `statusbar_api=ok` in the helper's diag.

## Decisions
- The dim stays drawn by the lock window, not the system dim layer (FLAG_DIM_BEHIND): the dim layer is a system window that counts for untrusted-touch occlusion too; on One UI a 0.88 dim layer dropped every replayed touch ("Dropping untrusted touch event due to Dim Layer"), a 0.45 one didn't.
- Testing on the phone: never use `cmd statusbar click-tile` right after a reinstall. SystemUI queues the click while the tile service is unbound and delivers it whenever the shade is next opened; on 2026-11-07 one sent at 10:13 started a touch lock at 10:25 when the owner opened the shade. Start sessions from the app's buttons instead.
- Testing overlays: don't use the Settings app as the app underneath. It hides other apps' overlays on its screens (`dumpsys input` shows the lock as NOT_VISIBLE, alpha=0), so anything "passes through". Check the lock's input state during the test.
- Full lock uses status bar disable flags with a server-held Binder token, not `IInputManager.disableInputDevice`: shell lacks `DISABLE_INPUT_DEVICE`, and the flags auto-clear if the helper dies.
- Pressing power ends touch lock and stay awake on purpose, as a guaranteed way out. The owner is fine with this (2026-11-03).
- The lock window is non-focusable (the app underneath keeps focus and is never paused); it takes focus only when it sees keyboard insets, which needs `FLAG_ALT_FOCUSABLE_IM` set from the start, and clears both flags together so the system treats it as a keyboard user.
- Injected touches are replayed rather than let through by making the lock non-touchable: a window can't pass on a gesture it already received, and a non-touchable lock would let fingers through too. The replay waits for any injected gesture still coming in, because Android's injection verifier takes one injected stream at a time (device id -1) and rejects a DOWN while another is down; for the same reason the helper ends a replay cut short by its exit with a CANCEL.
- Hold-to-unlock is timed with `SystemClock`, not an animator, so "Remove animations" can't turn it into a tap.
